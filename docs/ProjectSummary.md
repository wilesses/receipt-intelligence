# Project Summary

## Что делает проект

Receipt Tracker v2 - локальный трекер расходов по магазинным чекам. Он принимает PDF-чеки, извлекает из них текст, парсит товары, назначает категории, сохраняет данные в SQLite и показывает их через Flask web UI.

Главный объект проекта - не просто чек как сумма, а товарная строка чека. Поэтому большая часть аналитики строится по таблице `items`: категории, топ товаров, цена за единицу, динамика цены и сравнение текущей цены с историей.

Проект умеет получать чеки двумя путями:

- вручную через страницу `/upload`;
- из Gmail через IMAP endpoint `/gmail/fetch`.

Также есть пакетный импорт из папки `data/pdf_receipts` через `app/importer.py`.

## Как устроен проект

Запуск начинается в `run.py`. Он создает Flask-приложение через `app/web/app.py:create_app()`. При создании приложения вызывается `app/db.py:create_tables()`, поэтому таблицы и индексы проверяются на старте.

Ключевые файлы:

- `app/web/routes.py` - маршруты, SQL для страниц, часть расчетов;
- `app/db.py` - подключение к SQLite, схема, вставка чеков;
- `app/importer.py` - извлечение текста из PDF, OCR, подготовка данных, сохранение;
- `app/receipt_parser.py` - парсинг Rimi и Maxima;
- `app/category_keywords.py` - словарь категорий и порядок приоритетов;
- `app/analytics_service.py` - данные для графиков `/analytics`;
- `app/gmail_fetcher.py` - получение PDF из Gmail;
- `app/web/templates/` - страницы интерфейса.

`app/analytics.py` сейчас пустой. Реальная аналитика не там. `app/analy` тоже пустой файл и кодом не используется.

Данные лежат в:

- `data/receipts.db` - SQLite база;
- `data/uploads` - PDF, загруженные через web UI;
- `data/pdf_receipts` - PDF из Gmail или пакетного импорта.

### Импорт PDF

Ручной импорт идет через route `/upload` в `app/web/routes.py`. Файл проверяется как PDF, сохраняется в `data/uploads`, затем передается в `app/importer.py:process_pdf_api()`.

Gmail-импорт идет через `/gmail/fetch`. Настройки читаются из `.env`: IMAP-сервер, email, App Password, папка сохранения, глубина поиска, лимит писем, raw query и список отправителей. `app/gmail_fetcher.py:fetch_pdf_attachments()` подключается к Gmail, ищет письма, сохраняет PDF-вложения и возвращает списки новых, существующих и пропущенных файлов. После этого `/gmail/fetch` импортирует найденные PDF через тот же `process_pdf_api()`.

Дубликаты определяются по `receipt_number`, который берется из имени PDF без расширения. Перед вставкой `add_receipt_with_items()` проверяет наличие такого `receipt_number` в `receipts`.

### Извлечение текста и OCR

`app/importer.py:extract_text_from_pdf()` сначала пытается прочитать текстовый слой через `pdfplumber`. Если текст есть, он сразу идет в парсер.

Если текста нет, но на страницах есть изображения, проект считает PDF сканом и пробует OCR:

- конвертация PDF в PNG через `pdftoppm`;
- распознавание через `tesseract`;
- языки OCR: `lav+eng`.

Команды можно задать через переменные `PDFTOPPM_CMD` и `TESSERACT_CMD`. Если нужных программ нет, пользователь получает ошибку, что для скана нужен OCR.

### Парсер

Вход парсера - обычный текст. `parse_receipt(text)` удаляет пустые строки и решает, какой parser применить.

Если в тексте есть строка с `rimi`, вызывается `parse_rimi_receipt(lines)`. Rimi-парсер ищет дату рядом со словом `laiks`, итог по строкам `kopa`/`kopā`, товары по шаблону количества, единицы и цены. Название товара собирается из предыдущих строк.

Если Rimi-парсер не дал товаров, используется Maxima fallback. Maxima-парсер ищет дату по `YYYY-MM-DD` или `DD.MM.YYYY`, итог по строке `kopā apmaksai`, а товары по строкам вида `цена X количество`. Название также собирается из предыдущих строк.

Отдельного универсального определения магазина нет. Все, что не распознано как Rimi с товарами, фактически идет через Maxima-логику. Lidl есть в UI-фильтре аналитики, но Lidl-парсера в коде нет.

### Категоризация

Главная категоризация находится в `app/category_keywords.py:categorize_from_name()`.

Правила - это словарь `CATEGORY_KEYWORDS`: категория и список подстрок. Функция чистит название товара, оставляет слова длиной от 3 символов и считает совпадения keyword-ов. Если несколько категорий имеют одинаковый счет, выбирается категория по списку `PRIORITY`. Если совпадений нет, возвращается `прочее`.

В `app/receipt_parser.py` есть еще `categorize_item()`, но при импорте результат перезаписывается: `app/importer.py:prepare_receipt_data()` всегда вызывает `categorize_from_name()` для каждого товара. Поэтому фактический CategoryEngine для новых импортов - `category_keywords.py`.

Категорию можно поменять вручную на страницах чека и товара. Route `/item/<int:item_id>/category` обновляет только `items.category`. Это не меняет словарь правил.

Есть отдельный скрипт `app/categorize_existing_items.py`, который может перекатегоризировать существующие товары. Он не запускается автоматически из web UI.

### SQLite

В базе главные таблицы:

- `receipts`;
- `items`.

`receipts` хранит чек: `id`, `date`, `store`, `total`, `receipt_number`.

`items` хранит позиции: `id`, `receipt_id`, `name`, `canonical_name`, `quantity`, `price`, `category`.

Связь:

```text
receipts.id -> items.receipt_id
```

Практически вся аналитика использует `items.price`, а не `receipts.total`. Это важно: сумма чека на главной берется из `receipts.total`, но графики расходов по категориям, месяцам и товарам считаются по товарным строкам.

В текущей базе есть 355 чеков и 3519 товарных строк. Фактическая схема старой базы немного отличается от схемы, которую код создаст для новой базы: в существующем файле `receipt_number` не имеет `UNIQUE` constraint, а внешний ключ `items.receipt_id` без `ON DELETE CASCADE`. Код все равно проверяет дубликаты по `receipt_number` перед вставкой.

`canonical_name` - важное поле для объединения похожих товаров. В аналитике используется выражение:

```sql
COALESCE(NULLIF(items.canonical_name, ''), items.name)
```

Если `canonical_name` заполнен, товар группируется по нему. Если нет - по исходному `name`.

## Web UI и страницы

### `/`

Главная страница показывает список чеков. Данные приходят из `get_all_receipts()`:

```sql
SELECT id, receipt_number, date, store, total
FROM receipts
ORDER BY date DESC, id DESC
```

На странице есть счетчики: количество чеков, сумма и последний чек. Поиск по магазину и сортировка таблицы выполняются в JavaScript на клиенте.

### `/upload`

Страница загрузки PDF. Поддерживает drag-and-drop, выбор нескольких PDF и кнопку проверки Gmail. Ручная загрузка отправляет файлы на `/upload`, Gmail-кнопка отправляет POST на `/gmail/fetch`.

Ответы показываются как списки импортированных, пропущенных и ошибочных файлов.

### `/analytics`

Страница аналитики сама почти не считает данные. Она загружает JSON из `/analytics/data`.

`get_analytics_data()` считает:

- расходы по категориям;
- расходы по месяцам;
- топ-10 товаров;
- общий расход;
- средний расход в месяц.

Фильтры:

- начало периода;
- конец периода;
- магазин;
- категория;
- товар.

Графики строятся в браузере через Chart.js:

- doughnut по категориям;
- line по месяцам;
- bar по топ товарам;
- line для динамики цены выбранного товара.

### `/item/<name>`

Профиль товара. Использует `name` и `canonical_name`, чтобы собрать историю покупок. Показывает:

- среднюю цену за единицу;
- минимум и максимум;
- всего куплено;
- общую сумму;
- оценку текущей цены;
- алиасы товара;
- динамику цены;
- покупки по магазинам;
- все покупки товара.

Оценка текущей цены считается в Python функцией `build_price_evaluation()`. Если исторических точек меньше 3, оценка не показывается. Иначе последняя цена сравнивается с медианой: ниже 90% медианы - выгодно, выше 115% - дороже обычного.

### `/receipt/<id>`

Страница одного чека. Показывает позиции, категории, количество, цену и статус цены. Данные берутся из `items` по `receipt_id`.

`build_receipt_price_analysis()` для каждого товара собирает историю цен за единицу и сравнивает текущую цену с медианой. Итоговый блок показывает:

- всего товаров;
- дешевле обычного;
- дороже обычного;
- без истории.

### `/products/merge`

Страница объединения товаров. Она не была в исходном списке страниц для документации, но влияет на аналитику. Пользователь выбирает несколько названий и задает `canonical_name`. После этого аналитика группирует эти товары как один.

## Основные ограничения

Проект сильно зависит от формата чеков. Парсер не универсальный: он подстроен под Rimi и Maxima. Если магазин меняет layout, товары могут перестать находиться.

OCR есть, но зависит от внешних программ Poppler и Tesseract. Без них PDF-сканы не читаются. Даже с OCR результат зависит от качества скана и установленных языков.

Категоризация словарная. Она не знает товаров как сущностей и не обучается от ручных исправлений. Если название не содержит известных подстрок, товар попадает в `прочее`. Если есть несколько совпадений, результат зависит от `PRIORITY`.

В проекте нет таблицы ошибок категоризации. Поэтому нельзя точно сказать, какие товары чаще всего определяются неправильно. Можно только смотреть частые позиции в категории `прочее`.

В проекте нет найденных автоматических тестов и отдельной системы миграций. Из-за этого любые изменения схемы или парсера нужно проверять вручную на реальных PDF и текущей базе.

`receipt_number` берется из имени файла, не из тела чека. Если один и тот же чек пришел с другим именем файла, код может считать его новым. Если разные чеки имеют одинаковое имя файла, второй будет пропущен как дубликат.

Если нужно понять расходы, категории, цену, тренды или ошибки парсинга, начинать надо с того, как конкретная строка PDF превратилась в строку `items`.
